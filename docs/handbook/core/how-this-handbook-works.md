# How This Handbook Works

## Layers

The central repository `engineering-handbook` contains layers:

| Layer | Applies to |
| --- | --- |
| `core` | Every project. |
| `ios` | Apple-platform apps and Swift packages (iOS, watchOS, macOS). |
| `web` | Static sites and landing pages. |
| `kairos` | Kairos company projects only. Never synced into personal projects. |

Each project declares its layers in a `.handbook` file at its root:

```text
layers=core ios
path=docs/handbook
```

## Files in a project

```text
AGENTS.md              Entry point for people and AI agents. Contains a managed
                       block (between handbook markers) generated by the sync.
CLAUDE.md              Imports AGENTS.md (`@AGENTS.md`) plus Claude-only notes.
.handbook              Layers, target path, synced version, checksum.
docs/handbook/         Synced copy of the layers. Read-only. (`.handbook-docs/`
                       for sites published by GitHub Pages.)
docs/wiki/             Project-specific pages: overview, setup, structure,
                       integrations, and overrides.md (deliberate overrides and
                       known debt). Created from templates on the first sync;
                       never overwritten.
```

Only edit text outside the managed block in `AGENTS.md`.

## What belongs where

- **Handbook**: rules that are true for every project of that platform.
- **Project wiki**: facts about one project: setup, configuration keys,
  endpoints, screen-to-service maps, product decisions, and the concrete
  names of its shared clients and design-system tokens.
- **overrides.md**: rule IDs the project deliberately does not follow (with a
  reason), plus known debt: existing code that does not comply yet and must
  not be copied.

```markdown
| Rule | Decision | Reason |
| --- | --- | --- |
| IOS-ARCH-004 | Shared code lives in `Presentation/DesignSystem` | Design system is UI-only in this app |
```

## Changing a rule

1. Edit the page in the central repository, or edit the synced copy inside a
   project and run `handbook propose <project>`, which moves the change to a
   branch of the central repository and opens a PR.
2. Each rule change bumps `VERSION` and adds a `CHANGELOG.md` entry.
3. After merging, run `handbook sync-all` to update every project, then review
   and commit the change in each project.

## Writing a rule

- One rule per bullet, with an ID (`<LAYER>-<AREA>-<NNN>`), a level, and a
  *Why* when it is not obvious. Never reuse a retired ID.
- Mark rules checked automatically with `[lint]` or `[ci]`. Everything else is
  enforced by review.
- Prefer one concrete example to a paragraph of description.
- Do not put project names, hosts, keys, or company-specific types in `core`,
  `ios`, or `web`.
